# Project rules: Ruby Cocoon

These are the shared project instructions for Codex and Claude. `CLAUDE.md` imports this file; keep the rules here so the two agents follow the same guidance.

Apply these rules throughout the repository. The user's explicit instructions take precedence. The design rules below come from `README.md`, especially Controls, The journey, Systems, Art, UI and audio, Mobile, Editing the maps, and Tests. The touch usability and verification requirements make those design goals concrete. When an intentional design change alters a documented rule, update the relevant documentation in the same change.

## Before editing

- Read the relevant README section and inspect the existing implementation before changing a system. This is a Godot 4.8 beta 3 game written in GDScript, with no C#. Use matching 4.8.beta3 templates; preserve the independent 4.7 rollback cache documented in runbook 010c.
- Keep changes focused on the request. Preserve unrelated edits, downloaded source packs, and player data.
- Extend the existing shared components and data definitions before introducing a separate implementation. If documentation and behavior disagree, identify the discrepancy instead of silently inventing new design rules.

## Offloading to the local model

The user runs a local model on this machine: an OpenAI-style server at `http://localhost:1235/v1` with `qwen3.6-27b`, a 27B model that reads both text and images. It is much more capable than the earlier 8B model: besides test logs and first looks at screenshots, it can summarise and search code, review a diff for obvious mistakes and compare a screenshot with a reference picture. Since 2026-11-12 it no longer reasons before answering, so it is fast (a short answer in a few seconds, a screenshot or an 8 KB diff in about 15 s) but more agreeable: ask neutral questions ("describe the cliff edge", not "is there a rounded lip?"), and give it one clear question per call. `docs/visual_overhaul/runbook.md` lists what to offload in each overhaul step. Give it the subagent work and minor tasks first, to save tokens, before using a subagent or your own context on them.

- The sandbox blocks localhost, so the model and `server.py` are only reachable with sandbox network access enabled: run the checks, `server.py` and `tools/look.py` calls with the sandbox disabled (Claude: `dangerouslyDisableSandbox: true`). A failure from inside the sandbox doesn't mean the model is down.
- Check it once at the start of a task: `curl -s -m 5 http://localhost:1235/v1/models`. If it doesn't answer or the model isn't listed, proceed without it and do the work yourself (or in a subagent). Don't wait for it or keep retrying, and mention briefly in the reply that it was unreachable.
- Offload work where the input is large and the answer needed is small: running tests and reading the logs of the ones that failed, first looks at screenshots, summarising or searching long files, logs and diffs, and simple yes/no or list questions.
- Use the project's wrappers. `server.py` (`python server.py` in the background if `curl -s -m 5 http://127.0.0.1:5000/bionic/health` doesn't answer) has `POST /bionic/run` with `tests` (runs `tools/run_tests.sh` and returns its summary plus the model's reading of each failed log), `shot` (a harness screenshot and the model's answer to a question about it), `look` and `ask`. `python tools/look.py shot.png "question"` asks about an image, and `python tools/look.py --ask "question" file1 file2` (or piped text, such as `git diff`) asks about text. Calls are quick now, so ask in the foreground when you need the answer next. Still run full test runs and very large inputs (over about 50,000 characters) in the background.
- Keep work that needs judgement or correctness for yourself: writing and reviewing code, design decisions and anything the user will rely on. The model is approximate (the old one invented a door; the new one called the game's beasts Pokémon), so treat its answers as leads and confirm the ones that matter with a cheap check (grep, `tools/img.sh`, a small crop) before acting on or reporting them. Always read the `errors` that `server.py` returns, since the model may answer normally about a scene that failed to build.
- When delegating to a subagent anyway, tell it about the local model and these wrappers.

## Mobile and touch usability

- Treat phones and tablets as primary targets alongside desktop. Design within the existing 1280x720 reference viewport, landscape orientation, and expanding aspect ratio. Wide phones should gain usable space without stretching the art or clipping the interface.
- Use `UIKit` sizing helpers and shared constants in `scripts/ui/ui_kit.gd`. Interactive menu text uses 32 UI units; menu rows, page buttons and scroll buttons must be at least 56 UI units tall on desktop and 80 on touch. The one exception (the user's 2026-11-14 direction): menus opened while talking to someone or on the phone shorten their rows (down to 48 desktop / 60 touch, 28-unit text) so every choice shows without scrolling (`list_menu.gd` `COMPACT_ROW`). These are logical UI units, not raw device pixels. Touch sizing must apply even when the on-screen pad is hidden, including the title screen.
- Keep labels readable at normal phone viewing size. Never shrink text, rows, or touch targets to fit more content. Ordinary mobile choice lists belong toward the center and show several rows, with up/down moving the selection and scrolling it into view; choices can also be tapped directly. Use the shared scroll buttons (`scripts/ui/scroll_rail.gd`: up and down buttons at the ends of a scroll bar) or a scrolling detail pane for longer content. Beast information and the character creator must fit above the key guide and use scrolling when needed.
- During a film that takes input (the prologue) the pad shows only A and B, looking as they always do, with no added text; the d-pad, Start and Pause step aside, since nothing can move (`controls_overlay.gd` `set_film_mode`). A and a tap of B turn the page; holding B skips. The controls are named in the top-centre HUD (`A: Next  ·  Hold B: Skip`, with the scene's place under them), which shows for about four seconds as each scene begins and then hides; it returns while B is held, with a thin bar filling under it. Never leave a film without on-screen controls on touch, and put no other buttons or panels over it.
- The touch pad is painted by `controls_overlay.gd` at the screen's resolution (an off-white cross d-pad with dark arrows; A, B, Start and Pause the gem with white letters; held buttons deepen and a held arm fills with the gem); the user restored it on 2026-11-14 because the Kenney prompt pad was blurry. The keyboard strip uses small grey key caps; the controller illustration keeps Kenney's *Input Prompts* (`assets/ui/input_prompts/`).
- Keep the d-pad, A/B, Start, and Pause available with the mobile Start book and title menu. Modest overlap with menu borders or content is acceptable by the user's preference; keep essential choices and labels reachable. The ring editor may still move the side controls aside; the book's Map page keeps its towns clear of them instead. Respect device safe areas.
- Desktop Yes/No prompts show Yes and No side by side under the bubble or window, with an outline on the active answer (Yes by default); left/right moves it, A picks the outlined answer and B answers No. The picked answer fills with the gem (white text), the other disappears, and the selection sound plays. On mobile, A answers Yes and B answers No: animate the A/B buttons widening into labelled `A: Yes` / `B: No` gem pills, restoring their normal shape afterward (the restored 2026-11-14 pad). Whenever the touch pad is hidden (a controller or keyboard in use on a phone), show the desktop Yes/No answers instead, so the choice is always visible. Do not put Yes and No in a separate paginated list. Long question pages may use A: Next before the decision page.
- Every new action must be usable with touch and with the existing keyboard/gamepad actions. Provide visible tap targets and a usable focus order; do not require hover, a right click, precise dragging, or a physical keyboard for ordinary play. Show clear selected, pressed, focused, and disabled states, with labels or shapes as well as color where needed.
- Preserve one confirmation per press or tap. A single input must not activate a newly opened screen or multiple battle choices. UI taps must not leak through into world movement, and taps on or around the touch clusters must not reach menus behind them. Respect the touch clusters' enlarged hit areas and no-tap zones (`UI.touch_blocks`).
- Preserve the cardinal d-pad behavior: only one direction at a time, including boundary touches, unless the player has turned on the planned Diagonal movement setting (see World layout and navigation). Keep multi-touch working for B plus movement and the flute's button/direction chords.

## Interface style

- Interface text must sit inside a visible button or HUD window; never leave action labels floating over the scene. Desktop Yes/No actions use gem-filled buttons. List menus show no Select/Back buttons, since A and B already do that (the user's direction, 2026-11-13); rows can still be clicked or tapped. Touch confirmations retain the existing labelled A/B controls.
- Desktop spoken Yes/No prompts use two small reply bubbles below the speaker's bubble (see Mobile and touch usability for the outline and A/B). Menus opened while talking to someone or on the phone have no Leave row; a small gem "B: Cancel" button hangs under the menu's right end over its bottom edge (`list_menu.gd` `cancel_button`, `scripts/ui/edge_button.gd`). Hatching and level-up films end the same way with "A: Continue" under the stats window: the first A skips the stats' reveal, the next carries on; the egg drop has none. Keep complete sentences together when paginating speech; move the next sentence to the next bubble rather than splitting it. A single unusually long sentence may use a taller bubble instead of being cut.

- Build screens with the shared `UIKit`, existing window components, and the travel book's established structure. Keep spacing, frames, icons, bars, and feedback consistent with nearby screens.
- There is one interface style (the user's 2026-11-13 direction). Every window, the top-centre HUD and the touch controls are slightly rounded off-white boxes with a faint tint of the gem, with no border and no blur, a slight soft bezel (top edge lit, bottom edge shaded; the top-centre HUD has none along its top, which meets the screen's edge) and a soft shadow under windows (`scripts/ui/frame_box.gd` `draw_bezel`); body text on them is near-black. Buttons are the gem with white text. Use the window, row, button and slot builders in `UIKit`; do not add other window styles. The battle HUDs are the exception and keep their old look unchanged (see Battles below). The Start book is the other exception (the user's 2026-11-13 direction): its pages are light tan paper (`UIKit.book_paper`) with a faint painted grain, a soft spine at the fold between its two pages and gently darker page edges, and its unopened bookmark tabs are the same tan (`scripts/ui/book_paper.gd`, grain baked by `tools/book_paper/build.py`); its rows, buttons and text follow the shared style. Changing the book's tab, or opening a beast's Info from it, plays the page-turn sound (`Sfx` `page`). Speech bubbles are the one bright exception, reserved for spoken words: rectangular white bubbles with gently rounded corners, subtle shading, the same soft bezel and a soft shadow, with dark text and the speaker's name in white on a small gem-coloured plate at the top-left. Anchor them to the speaker's stable head position, snap to screen pixels, flip below the head near the top edge, and slide the chevron along the edge while keeping the bubble inside the safe area and clear of touch clusters. Phone calls and off-screen voices use a stationary bottom-centre bubble without a chevron. Written signs, necessary descriptions and system prompts use the shared off-white window without speech sounds. Films follow the same rule (`scripts/ui/cinematic_dialog.gd`): spoken lines are speech bubbles on their speaker, and each line fits one page since it advances on its own. A film establishes what is happening only through characters talking to each other: no narration, captions or title cards.
- The Codex (`scripts/ui/codex.gd`, `codex_head.gd`, topics in `scripts/data/codex_db.gd`) explains every battle mechanic after the Coastal Path's four lessons (the user's 2026-11-14 direction; there is no Bestiary). It is an orange robot head (Quaternius's robot, head only, flat-fronted eyes) at the top-left of the screen with a subtle bluish glow behind it and no window; its white speech bubbles hang under it, the glow stays beneath the bubble, its brows change with the mood of each bubble, and it sometimes starts one with a beep. It only offers topics the player is eligible to know (nothing about gear, songs or summons they don't have yet). Asking it never uses a turn (Codex with a ? icon on the trainer's bar, a tap on the head, the Start book's Codex page). Settings ► Codex tips switches its chime-ins off; on a journey played over three hours before it existed, it switches them off itself and says so.
- Through-door replies are speech: anchor their white bubbles to the closed door, above its top or below its bottom as screen space allows. Keep the full bubble and name plate within the safe area and clear of touch controls, for both outdoor and indoor doors.
- Support all four gems (**Ruby**, **Sapphire**, **Emerald**, **Hematite**) and runtime changes to the gem; Ruby is the default. The gem is a faint tint in the windows' off-white, and fills buttons, the focused row, bars and filled (selected) slots; headings use a deepened gem. Body text stays near-black; never lighten red into pink. Derive colors from `UIKit`; avoid hardcoded palettes in individual screens.
- States: a focused or selected list row is a rounded gem bar with white text; a standalone button is the gem with white text, with a thin dark ring while focused; pressed is a deeper gem; disabled is dim text (a plain off-white well for a standalone button). Focused tiles and cards get the thin dark ring (`UIKit.focus_ring`). Labels inside a lit row turn white with it (`UIKit.follow_row`).
- The title screen's menu is one gem button low on the screen (gently rounded, blurred art behind it, most opaque across its middle), showing one choice, with ▲/▼ arrows above and below it (none when New Game is alone); up/down slides the words inside the button, cropped at its edges, looping forever (`scripts/ui/title_carousel.gd`, the user's 2026-11-14 direction).
- Short messages (place names on entering a town, road or building, pickups, gold, battle messages) go in the top-centre HUD (`UI.top_bar`); nothing slides in at the top left. It has exactly three sizes (small: one line, 360 units; medium: one line, 640; large: two lines, 640) and every message fits one of them; text never shrinks, and a longer message is split into pages.
- The battle HUDs' blur must work on the Mobile and Compatibility renderers; where it costs too much, `UIKit.set_blur(false)` gives them a plain box at higher opacity.
- Use **Quattrocento Sans** for the interface: **Bold** for names/headings (`UIKit.font_head`); **Bold and upper case** for small text, which is captions, tags, short values, hints and damage numbers (`UIKit.font_bold`, `UIKit.small_caps`, and any `UIKit.label` asked for under 24 units); **Regular** for ordinary body text, menu actions and descriptions (`UIKit.font_body`; pass 24 or more to `UIKit.label` for a description in the small size). This is the user's 2026-11-12 direction, replacing League Spartan and PT Sans. Use **Fuzzy Bubbles** for spoken dialogue (`UIKit.font_dialog`) at 29 UI units (about 10% smaller than the previous 32). World-object lettering uses **Noto Sans Old North Arabian** with a shared deterministic English-to-glyph substitution map; never display English lettering on 3D world objects. Keep underlying English for interactions/accessibility. UI/dialogue remain readable English. Use Cormorant SC Bold for the 3D intro/title logo, including DEMO (the user's 2026-11-13 direction). Bundle licenses and verify glyph coverage. Use `UIKit.body_px` / `head_px`, preserve readable sizing and touch targets, and never shrink text to fit. Keep dialogue top-aligned and normally three lines per page. This is the user's 2026-11-12 direction.
- Keep HUD information contextual. Outside battle, readouts appear when needed and fade; new information belongs in the top bar, a speech bubble or a menu beside its subject. Do not add permanent status panels.
- Battles use the cinematic HUD, which keeps its own look (unchanged by the 2026-11-13 off-white restyle: square, bordered and dark where described here; `FrameBox.legacy`, `UIKit.BATTLE_*`): a flat silhouette outline on the chooser and targets (your trainer in the gem colour; beasts in their ring's facing element, wild beasts in their own; one line round the outside, never an inverted hull across the model's features), one compact chooser bar at a time (you first, then each beast) and a translucent yellow 3D target arrow (a slim flat shaft and a long four-sided pyramid head, without camera-facing ribbon strips). The battle bars are the one exception to the dark window style, by the user's choice: one white shape with dark text, framed in their model's outline colour, its left edge leaning in at `TopBar.TAPER`: the level in small black text, a thin divider, small ◄ action ►, and full-width square HP/MP gauges in white borders along the bottom inside it (small right margin, flashing MP cost). The chooser's bar has a ▲ / ▼ above and below where up / down leads somewhere, or a short thick rounded line where it doesn't. A bar stands to the left of its model, slides out from behind it and runs behind it so its frame meets the outline; it is drawn over other beasts. While aiming the chooser's bar reads "Bite ► Target" with a short, centred yellow pointer, and each target gets its own bar. A round icon stands before the action's name (`scripts/battle/action_icons.gd`): its element's colour for an elemental attack, grey for a plain attack, navy for anything that isn't an attack, each with its own glyph. While an attack is aimed, a target weak to it shows a red burst after its name and one that resists it (its own element) a slate shield. What the action does goes in the top-centre bar. The 3D arrow stays yellow across gems. Do not restore fixed grids or shield panels. Bars show only while something is being chosen; during actions none appear. While your trainer chooses, each beast without a bar shows stacked HP-over-MP gauges with regular HP/MP values on their left and each trainer a "SHIELD" label and their shield orbs, in small plates with the battle HUDs' dark fill, no frame and no slant, the fill and a thin white bottom line both fading out at the sides; none of these show while a beast chooses. Trainer shield orbs appear only while targeted or hit. Preserve lesson restrictions, automatic targets, one confirmation per press, and two taps to aim/confirm a 3D target. The chooser's bar taps as a full `UIKit.row_h()` row; bars keep safe areas and the touch clusters' enlarged no-tap zones, resting nearby with a pointer when neither side of their model fits.
- A weapon's beat attack (`scripts/core/beat_chain.gd`, `scripts/battle/beat_cue.gd`) keeps its cue minimal: a white ring with a soft dark halo above the target, a notch spinning to the music's beat that meets the mark at the top on the beat, pips for the hits allowed and landed, and the grade (Perfect, Good, Miss) in Quattrocento Sans Bold beside it; the gem shows only in the glow of a landed hit and a critical finish's pip. It stays inside the safe area, under the top bar and clear of the touch clusters. A press of A (on-screen, keyboard or gamepad) or a tap on the ring counts once; nothing else on screen does. Chain length follows trainer level (none below Lv 4); foe trainers roll their hits instead of playing, and only bosses and arena masters use weapons.
- Battle scenery encloses the whole stage. Outdoor, fishing and arena backdrops use continuous biome artwork on a textured surround, with a curved floor blend and small batched clusters of regional props around all four perimeter corners to hide joins. Indoors retain their walls/ceiling with columns and lower props covering wall junctions. Keep trees on land in fishing scenes. Hide ground/sky seams and keep the painted surround clear of the camera; use the offline backdrop baker and shared smoothing pipeline. Use the shared battle lighting's soft warm key, cool rim and darker colored perimeter; avoid bright flat ambient light and keep the fighting area readable. Preserve readable 3D ring turns, dim empty pads and fainted beasts lying on both trainers' pads.
- Battle cameras use the shared named-shot director: opening, choosing, attacker/follow/reaction/return, summon, capture, knockout, victory and beat (held on the target through a weapon's beat attack). Keep at least half a second between shot changes, add no action waits, and constrain every camera position and shake inside the enclosed scenery. Cache surround geometry and scenery assets; only fighters cast shadows. Audit several angles per setting and record before/after frame times on phone hardware when available; desktop Mobile-renderer timings must be identified as desktop measurements.
- Hide foreground battle scenery and any individual prop instance between the camera and a fighter, restoring it when the view clears. Keep the field readable in every directed shot, including reverse views past indoor columns. Preserve the sealed floor, room shell and surround, and retain the far corner dressing that conceals visible joins.


## Art and animation consistency

- The 3D world looks modern, cozy, clean and stylized, with *Animal Crossing: New Horizons* as the primary reference for environmental cohesion: deliberate rounded forms, soft tactile painted materials, consistent turf lips, banks and shorelines, organized leaf-cluster foliage and soft light (the user's direction, 2026-11-12, replacing the earlier *Fortnite* reference). Learn its principles; never copy its models, textures, triangle grass motif, characters or interface. Colour sits between soft and punchy: gentle, slightly warm colours with clear light/shade contrast, the strongest saturation kept for people, beasts, flowers, fruit and interactables, never a neon lawn. Ground carries the game's own subtle per-biome motif. People and beasts keep their proportions and identities but are remodeled to the same standard; regions keep their architecture and per-biome cliff shapes; dark places stay seriously dark in the same visual language. The full standard, checklist, audit and the small-step plan live in `docs/visual_overhaul/`; follow its numbered `runbook.md` ("Run runbook step NNN"; `README.md` there says which step is next) and work one step at a time and finish its evidence before starting another. Pause for screenshot approval when game visuals change; completed nonvisual tooling and measurement steps may continue automatically, as the user directed on 2026-11-12. It must never look gritty or retro: no PSX/PS2-era treatment, voxel or blocky shapes, or pixelated textures anywhere in the 3D world (the user's direction, 2026-11-12). Every 3D object carries a texture (a painted image or a texture-sampling shader), not a bare flat colour; only light, shade and glow effects (contact shadows, cast glows, target arrows, beat cues, summon effects) may be untextured, and `--scene=texture-audit --verify=1` lists any that aren't. Simplify a model's geometry rather than lose frame rate. Match nearby assets' scale, palette, texture density, lighting and level of detail, and avoid photo-realistic materials. This direction covers buildings, environments, props, furniture, people and beasts; the HUD and interface keep their own styles described under Interface style.
  - Textures read as clean and painted: soft gradients, gentle shading, and clear shapes (brick courses, boards, shingles, leaves) without grain, speckle, harsh black cracks, or visible texel blocks. Never sample world, terrain, building, prop, or furniture textures with nearest filtering; use `TEXTURE_FILTER_LINEAR_WITH_MIPMAPS_ANISOTROPIC` (or `filter_linear_mipmap_anisotropic` in shaders). Pixel-art icons on shop signs and other graphic glyphs may stay sharp.
  - New or re-baked world textures go through `scripts/gfx/smooth_texture.gd` by running `tools/smooth_textures.gd` (then `godot --headless --path . --import`). It records what it smoothed in `tools/smoothed.json`; never smooth a texture twice or hand-edit that record.
  - Keep borders between ground layers soft and curving rather than stepped. Prefer warm, softly saturated colors with clear contrast over gritty, muddy or neon ones. Do not add PS1 artifacts such as vertex snapping, affine texture warping, color banding, or low-resolution rendering; functional dithers that keep the player visible (terrain `hole`, wall fading) stay.
  - Waterfalls are closed shapes, like buildings: no edge of the falling sheet, the river above or the pool below may float or show as a bare cut from any place the gameplay camera can be. The sheet spans the channel bank to bank and its sides tuck into the cliff and banks on both sides; its top lip flows continuously out of the upper river's surface (no thin slab, ledge or visible thickness at the brink); it sits against the cliff face with no gap or see-through strip behind it; and its foot disappears into the lower water under foam or splash rather than ending on a hard line. Nothing (ground, void or the cliff's raw edge) shows between the water and the rock around it. Seal it in the terrain/water builder, not by relying on one camera angle or on props standing in front, and check it from the real gameplay camera, including a close crop of both sides and the lip.
  - Lighting stays soft: filmic tone mapping, gentle glow, ambient occlusion, and blurred shadows. Respect the mobile and web renderers when adding any effect.
- Reuse the established asset packs, importers, shaders, and procedural builders. Inspect the relevant README screenshots and an in-game view when choosing or changing art; filenames alone are not evidence that an asset fits.
- Use `scripts/gfx/beast_model.gd` as the common beast rendering entry point for the overworld, battles, and portraits. Keep line colors in `scripts/data/beast_looks.gd`. Ghosts remain recognizable versions of their beasts in black and purple with smoke, and merges must visibly combine their parents' parts.
- Beasts' battle poses (attack, cast, Defend, block, hit, faint) work for every body kind from the rig's measured limbs, so ghosts and merges inherit them; play them through `beast_model.gd` (`pose_*`), which also gives the old legendary and robot models whole-model versions. Plain attacks lunge; every other move is cast with its element's glow, the camera cutting to the caster and then to where it lands. Hit poses, bursts and damage numbers land on the same frame. Check changes with `--scene=newbeasts --anim=cycle` and `--scene=battle-poses`.
- Preserve each region's architectural identity and the recognizable functions of buildings. Shops need their shop fronts and signs; Beast Centers are the same small temple everywhere (`beast_temple.gd`: grey stone blocks, gold-trimmed gable, blue door, golden dome), and inside they match it (the same blocks) and work by magic, with relics rather than machines; kennels are barns on the roads, never in towns. New props and landmarks should look native to their town and remain readable from the gameplay camera.
- Keep characters grounded, correctly scaled, and facing the intended direction. Match movement animation to travel speed, avoid sliding feet or floating models, and preserve readable idle, walk, talk, and attack poses.

## Building exteriors and scale

These apply to every outdoor building in every town and style (Cocoon Cove's kit, the PS1 House Pack houses, the wall-section builders, Creole, frontier, island and landmark builders), to scenery houses and to anything new.

- From outside, no building may show its inside, from any place the gameplay camera can be. No open doorways, panes left out of windows, gaps at corners, eaves, roof edges or between pieces, missing or inward-facing (culled) wall faces, or see-through wall materials. Doors are closed leaves; window glass is opaque (painted glass and reflection marks, never transparent, never a room behind it). Rooms are only seen after entering, in their stage rooms. Only structures designed open-air (porches, galleries, arcades, market stalls, arena stands) may be open, and they show no room behind them. Seal a building in its mesh or builder, never by relying on one camera angle or on what happens to stand in front of it.
- Keep buildings to the people's scale: one tile is one world unit and the hero stands about 1.44 units tall. Every front door is at least the game's full-size door (`house_models.gd` `DOOR_H`, 1.8 units and about 0.85 wide: never under 1.7, clearly taller than the hero) in every town; a style may have taller doors (the wall-section builders' and Creole doors are about 2.3), never lower ones. A ground storey rises clear above its door, so eaves, porch roofs, awnings and signs start above the door's top rather than at head height; storeys are roughly 2.3-2.8 units each. When fitting a pack or kit building to its plot would shrink its doorway, stretch its ground storey (`house_models.gd` and `cove_buildings.gd` `warped()`) instead of accepting a low door or storey; upper storeys and roofs keep their proportions. Never resize people, or put a door on that is larger than its wall, to compensate.
- Windows are in proportion to their storey and wall: sills about at the hero's waist, heads below the storey's top, matching the building's other windows, and never wider or taller than the wall section that holds them.
- Doors, frames, windows, shutters, sills, signs, awnings and lamps are attached to the wall they belong to. A door leaf sits in its frame within about 0.1 of the wall face around it; windows are set into the wall with their frames and sills touching it. Nothing floats in front of a wall or hangs in the air, and nothing sinks behind the wall face where it is hidden or flickers. When replacing a pack's own door or window, cut the original away together with any slab or frame it stood out on, seal behind it, and line the new one up with the map's door tile (as `house_models.gd` `dressed()` and `cove_buildings.gd` `warped()` do).
- After changing buildings, run `bash tools/run_tests.sh exteriors` (`--scene=exteriors`: sealing, door height and door attachment for every town building) and, for Cocoon Cove's kit, `cove-exteriors`; then look at the buildings from the real gameplay camera, including a close crop of their doors and windows beside the hero.

## World layout and navigation

- Preserve four-way, whole-tile movement and completion of a started step at the next tile's center. Keep keyboard, gamepad, and touch movement consistent. The hero, NPCs and beasts always come to rest on tile centers. Planned (user's decision, 2026-11-12; `docs/visual_overhaul/steps.md` Phase M): an eight-way "Diagonal movement" setting on every platform, off by default. A diagonal step needs its destination and both side tiles free (no corner cutting). Cliffs, building walls, paths, water and other terrain edges may run diagonally, but every tile stays whole (walkable or blocked), diagonal cliff tiles stay unenterable, and every diagonal path stays navigable in four-way movement.
- Respect elevation for movement, interaction, and line of sight. People, doorsteps, and buildings belong on level ground; ramps and stairs must be approached from their intended ends.
- Place signs on verges beside paths, never on paths, paved walking lanes, bridges, or door approaches. Keep them readable and reachable from adjacent level ground.
- Keep roads, exits, doors, NPCs, and puzzle targets visible and reachable. The camera looks north from the south: avoid tall objects just south of a path or other important walkable space, including on elevated ground. Preserve the existing wall/building fading and terrain dithering that keep the player visible.
