# 009b: first-visit/cache investigation (in progress)

12 November 2026. This is a checkpoint, not completion of 009b. The roughly 1.5 s
desktop first-visit goal has not been demonstrated on an initially cold packaged
launch, and Web improvement has not yet been measured. Do not advance to 010b.

## Accepted desktop experiments

All rows below are continuous black holds, in milliseconds, measured from the
completion of fade-out through the call to fade-in. They include synchronous
arrival work and the first draw. Legacy frame-sampled `black_ms` remains in the
raw reports but can miss synchronous stalls. All accepted runs have two passes,
four arrivals per pass, zero benchmark problems and zero focus losses. These are
desktop AMD measurements at 1920×1080/Mid, not phone measurements.

| Experiment | Path | Cove | House | Rue |
|---|---:|---:|---:|---:|
| Native OpenGL, shader cache on | 23383.0 | 5528.1 | 3872.5 | 1358.4 |
| Native OpenGL, shader cache off | 2483.2 | 874.9 | 344.8 | 528.0 |
| Native OpenGL, cache on control | 22975.7 | 5446.1 | 3552.2 | 1357.1 |
| ANGLE, cache on | 25358.6 | 12382.8 | 5492.7 | 2040.1 |
| Packaged Compatibility, first measured launch, cache off | 13810.6 | 7088.5 | 3259.6 | 1218.6 |
| Same packaged build, later focused launch, cache off | 1272.0 | 1133.4 | 301.5 | 460.9 |

The on/off/on comparison strongly associates the recurring native OpenGL stall
with the engine shader-binary cache path. It does not isolate a specific driver
API. ANGLE with caching enabled is slower here and is not selected. No cache
files were deleted. The read-only probe found 671 runtime cache files (125,046,115
bytes) and 88 project cache files (2,378,056 bytes).

The two packaged launches demonstrate a separate initial shader-use cost. The
later launch meets the per-map goal with an already exercised driver cache; this
does not establish a cold-driver guarantee. Their existing title script-loading
waits, measured separately, were 941.2 and 696.3 ms respectively. Shader work has
not been moved behind the title. Second-pass arrivals across these experiments
are roughly 36–374 ms.

## Prototype and renderer scope

`tools/vo_windows_compat.py --benchmark` clones the existing Windows preset into
a dedicated benchmark export with the custom feature `compatibility_build`.
That feature selects Compatibility and disables only its engine shader cache.
The actual exported executable was run without renderer/cache command-line
overrides and reported OpenGL, the expected driver, and caching disabled.
Normal export presets are restored byte-for-byte; normal Forward+/Mobile cache
settings remain enabled. This is an experimental dedicated profile, not a
completed release or a Web fix. The existing per-map `_warm_shaders` is unchanged.

Godot's [pipeline documentation](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html)
limits shader baking to Forward+/Mobile. Compatibility/Web cannot use that baker.
In the [matching engine source](https://github.com/godotengine/godot/blob/5b4e0cb0f/drivers/gles3/shader_gles3.cpp),
native cache restoration calls `glProgramBinary`; the Web cache-load path returns
false. A native cache workaround therefore cannot establish Web improvement.

Windows export templates were obtained from the official 4.7 release using HTTP
ranges. Complete extracted entries passed ZIP CRC checks and have recorded SHA256
hashes in `build/tools/godot-windows-templates/4.7.stable/provenance.json`. The full
1.28 GB archive digest was **not** verified because only the required entries were
downloaded. Global templates/installations were unchanged.

## Continuation (Claude, after Codex's session ended)

**Capture comparison.** `build/perf/vo/009b/capture-compare.txt` diffs each arrival capture against
`before-load` (cache on). Cache off, both packaged runs: 0.08–0.42% of pixels, confined to the characters'
idle poses and a sign (masks in `build/shots/vo/009b/compare/`): animation timing, not a rendering change.
ANGLE differs across the whole frame (0.15–2.39%), consistent with a different GL implementation; it is not selected.

**Shared warm-up experiment: no measurable effect, not adopted.** Codex's opt-in key (exact materials plus
geometry format instead of mesh RID) crashed on `PrimitiveMesh` (`surface_get_format`, then
`get_blend_shape_count`, are `ArrayMesh`-only). The two partial runs are kept with `INVALID.txt`. After the fix,
`shared-warmup-cache-off-3` against a same-session control `cache-off-control-2` (both cache off, load-only, two
clean passes, no focus losses):

| Map, first visit | Control: draws / ms | Shared: draws / ms |
|---|---:|---:|
| Path | 134 / 2322.1 | 53 / 2316.2 |
| Cove | 190 / 801.2 | 73 / 810.1 |
| House | (no warm-up) / 296.6 | (no warm-up) / 302.9 |
| Rue | 272 / 466.5 | 108 / 467.8 |

Cutting warm-up draws by about 60% changes nothing, so the first-frame wait is shader compilation per distinct
shader, not per-draw cost. The option stays opt-in for diagnostics; ordinary play keeps the existing warm-up.
`vo_cost.py --warmup-shared` and the summary's new columns record this. The editor's first Path visit also
contains a 564 ms world-script wait (hidden behind the title when `--title_ready=1`, as the packaged runs do) and a
394 ms one-off first-battle prewarm that the packaged build doesn't show (under 20 ms there).

**Web (Codex's accepted run, `web-before-validated`, 1920×1080, title-ready):** first visits 1384.3 / 1317.6 /
333.6 / 567.6 ms; second pass 176.0 / 286.5 / 67.9 / 411.2 ms. Web is already within about 1.5 s per map.

**Web shared warm-up (`web-shared-warmup`): inconclusive, no improvement shown.** Two clean passes, no focus losses
and no problems, with the same draw reductions (53/73/108). First visits were 1585.0 / 1405.2 / 6204.9 / 2219.6 ms,
second pass 199.0 / 316.6 / 87.9 / 439.3 ms. The run isn't comparable to the baseline: the pane's window was
2400×1350 (rendering 1920×1080), and the first attempt began in a hidden, smaller pane before being reloaded. The
house has no warm-up, so its 6.2 s is a browser or pane stall, not an effect of the option. The only console error is
the known `SampleNode._pause` audio TypeError. Together with the native result, this gives no reason to adopt the
shared key.

Checks after these edits: quick, transitions and title-startup pass (`final-*.json`). The local model's diff review
flagged four issues; all were false (GDScript integer `for` loops and `a if c else b` are valid, and the run that used
this code finished cleanly).

## Where 009b stands

- Desktop Compatibility: the dedicated `compatibility_build` profile (cache off) takes the Path from 23.4 s to
  2.3 s in the editor, and to 1.27 / 1.13 / 0.30 / 0.46 s in the packaged build once the driver has seen it. That
  meets the goal of about 1.5 s per map, except on the very first launch of a newly installed build (13.8 / 7.1 /
  3.3 / 1.2 s), when the AMD driver compiles every program for the first time.
- Web is within about 1.5 s per map before any change. Neither the native cache fix (Web can't load cached
  binaries) nor the shared warm-up improves it, so "the web improves measurably" is **not** met.
- The only remaining lever for both the cold launch and Web is compiling fewer distinct shaders, or compiling
  them before the first map. Compiling them behind the title would change what the player sees: the title would stall
  or need a "preparing" state while about 13 s of cold compilation runs. Reducing shader variants touches many
  builders and can change materials. Either needs the user's decision and screenshots before it is implemented.
